# Sketchbook boundary and thumbnail review

- [finding] At `8d3b3d7`, canonicalizing the configured `sketches/` path accepted a directory symlink. A real project B pointing `B/sketches` at existing `A/sketches` caused discovery to expose A's saved gallery entries under B; the same canonical-root equivalence let IDs open across the alias.
- [evidence] TDD red: `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml rejects_a_symlinked_sketchbook_and_stale_ids_when_both_roots_exist -- --exact gallery::tests::rejects_a_symlinked_sketchbook_and_stale_ids_when_both_roots_exist` failed before the production guard because `discover(alias/sketches)` succeeded. The test creates valid A/orbit, a separately existing B/sketches/orbit with different source, and B/aliased-project/sketches -> A/sketches.
- [decision] A configured sketchbook must itself be a real directory according to `symlink_metadata` before canonicalization. Gallery discovery and stale-ID opening share this boundary check; document sidecar/thumbnail ownership uses it too. Explicitly selected source files remain openable when their configured sketchbook is a symlink, but their neighboring sidecars are not claimed or rewritten.
- [evidence] The Unix-only root-link regression now rejects discovery and old IDs for a symlinked configured sketchbook, rejects stale IDs against a separate existing B root containing a same-named sketch with different content, and confirms standalone selection leaves its sidecar and thumbnail untouched. Windows builds do not compile Unix symlink fixtures.

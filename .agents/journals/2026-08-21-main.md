# Semantic Variables, Assignments, and Lexical Scope

## Summary

The previous journal ended with a traversal-only `Analyser` that walked every AST node and always returned an empty diagnostic list. The analyzer now resolves names in source order, reserves direct global names program-wide, enforces revision 2.2 lexical scopes, validates declaration and assignment sites, and reports exact token-based diagnostics.

The work spans specification revisions 2.1 and 2.2. Revision 2.1 established the name-resolution, reservation, diagnostic-priority, and assignment rules but briefly specified flat ordinary blocks. Revision 2.2 superseded that model with lexical scopes for every `if`, `else`, `repeat`, and animation `loop` body.

The implementation and tests are committed through:

- `9521486 feat(analyser): add scope for variables and functions`

`main` is synchronized with `origin/main` and the working tree was clean when this journal was written.

## Specification and Documentation

- [decision] Direct top-level variables and functions share one global namespace. Their names are reserved throughout the program, including before their declarations, while visibility still follows source order.
- [decision] Functions are not hoisted for calls. A function is registered immediately before its body is analyzed so recursion works.
- [decision] A declaration cannot reuse a visible name in the same or an enclosing scope. Separate non-overlapping local or block scopes may reuse a name unless a direct global declaration reserves it.
- [decision] Every `if`, `else`, `repeat`, and animation `loop` body introduces a lexical block scope. Block declarations are visible in that block and its nested blocks but not afterward.
- [decision] Then and else branches are separate sibling scopes.
- [decision] Repeat range expressions are analyzed before the repeat variable enters the repeat-body scope.
- [decision] Name diagnostics use short, exact wording with final punctuation. Examples include `Cannot find name 'x'.` and `Cannot declare 'x' because that name already exists.` The GIC-owned declaration and assignment variants follow the same style.
- [decision] Assignment to a user function reports `Cannot assign to function 'f'.` at the assignment target.
- [decision] `docs/Language specification.md` is the stable active specification path. Its frontmatter carries revision `2.2`; historical specifications remain versioned under `docs/deprecated/`.
- [lesson] Versioned active-specification filenames caused broad link churn and briefly produced commits whose links pointed at files added only by the next commit. A stable active path prevents that repeated migration.

## Analyzer Implementation

### Basic declaration and assignment checks

- `a55729d` added assignment-target resolution and the first `Cannot find name` diagnostic.
- `1ee97e0` added duplicate variable declaration diagnostics.
- `2dc4bc8` changed variable processing to analyze the initializer before registering the declaration. This rejects self-reference such as `let count = count;` and added missing-name checks for identifier reads.
- `a3aec3e` added declaration and assignment protection for GIC-defined names. Reserved-name checks run before ordinary missing/duplicate checks so the intended primary diagnostic wins.

### Source-ordered scopes and global reservation

- `02cdfd6` introduced `src/scope.ts`, a scope stack, and innermost-to-outermost lookup through `findDeclaration()`.
- The analyzer creates one global scope, pushes a function-local scope for each function, and pops it after the body.
- Parameters and direct function-body variables live in the function-local scope. Functions can read and assign previously declared globals, while parameters and locals do not leak.
- `programGlobalNames` is collected from direct top-level variables and functions before source-order analysis. It reserves names without inserting later declarations into the visible global scope.
- Function names are inserted before walking their bodies, enabling recursion without allowing calls before declaration.
- `2577955` extended validation to function names, parameters, and repeat declaration sites.

### Lexical control-flow scopes

- `fa96ab4` analyzes repeat bounds before creating the repeat scope, validates the iterator against GIC names, visible declarations, and later global reservations, then walks and discards the body scope.
- Repeat tests cover iterator visibility, range-expression ordering, GIC-owned names, collisions with visible or later-global names, sibling reuse, and declaration lifetime inside the body.
- `2eb5cc4` added one scope around each complete then branch, else branch, and animation-loop body.
- Block tests cover top-level and function-local declaration lifetime, nested reads, sibling reuse, visibility throughout an else body, and global no-shadowing.

### Declaration kinds and assignment legality

- `9521486` changed each scope value from a raw `Token` to a declaration record containing the token and `kind: "function" | "variable"`.
- Functions are registered as `"function"`; ordinary variables, parameters, and repeat variables are currently registered as `"variable"`.
- `onAssignment()` resolves the declaration once, reports missing targets or function targets, and always walks the assigned value so independent RHS diagnostics are not suppressed.
- `src/analyser-diagnostics.ts` owns the current name-related diagnostic constructors, including assignment to a user function.

## Lessons and Failed Approaches

- [lesson] Global reservation and source-order visibility are different questions. Putting every reserved global into the visible scope would accidentally hoist later declarations.
- [lesson] Register a variable only after analyzing its initializer; otherwise self-reference appears valid.
- [lesson] Analyze repeat start, end, and step expressions before registering the iterator; otherwise the iterator is incorrectly visible in its own range.
- [lesson] A scope must surround the complete block, not each statement. An early `if` implementation pushed and popped inside the statement loop, so a declaration disappeared before the next statement. A nested-block read made the defect observable.
- [lesson] Then and else need separate push/walk/pop lifecycles. A multi-statement else fixture protects both visibility within the branch and disappearance afterward.
- [lesson] The animation `loop` must be the final program construct, so a test that uses a loop-local name after the block is invalid GIC. The stale TODO was replaced with valid loop declaration-site coverage; the implementation still gives the loop body its specified scope.
- [lesson] Passing a callback to `test.todo()` does not activate the test. Node still reports it as TODO until `test.todo` is changed to `test`.
- [lesson] Diagnostic offsets are absolute. In `func f(){return;}f=2;`, the assignment target is `[17, 18)`; `[13, 14)` points inside `return`.
- [lesson] Raw declaration tokens became insufficient when assignment legality depended on whether a visible name denoted a function or variable. Store the semantic kind with the token rather than maintaining a parallel function-name set.
- [lesson] Assignment-target errors must not stop traversal of the assigned value. The analyzer collects independent diagnostics at different source locations.
- [lesson] A partial helper move removed `Analyser.missingNameDiagnostic()` but left identifier resolution calling it, causing four runtime test failures. Complete every call-site migration or keep the original helper until a focused refactor.
- [preference] During interactive TDD, Fabian runs focused tests and reports `red`, `green`, or `all green`. The agent runs tests only when explicitly requested and trusts those reports between requested verification points.

## Identifier-Only Call Targets

### Decision and Documentation

- [decision] GIC calls use bare identifier targets for built-in and user-defined functions. Literals, grouped expressions, and call results are not callable syntax; arguments remain full expressions.
- [decision] The parser reports `Only function names can be called.` at the opening `(` that attempts a non-identifier call.
- [decision] Callable runtime objects may remain interpreter internals but are not user-visible expression values.
- `819a8f7` recorded the decision in the active specification, memory, parser guidance, and dependent semantic/interpreter milestones.

### Parser and AST Alignment

- `8b275e1` narrowed `CallExpr.callee` from `Expression` to `IdentifierExpr`.
- `Parser.call()` still returns `Expression` because the precedence level also returns literals, groupings, and bare identifiers when no argument list follows.
- `Parser.finishCall()` accepts `IdentifierExpr`; the parser checks the current expression after consuming `(` and throws when it is not an identifier.
- Keeping the existing loop rejects chained calls naturally: after the first call, the current expression is a `CallExpr`, so a second `(` fails the same identifier guard.
- Parser-expression tests pin the exact message and opening-parenthesis span for numeric (`42()`), grouped (`(circle)(1)`), and chained (`makeThing()(1)`) targets.
- `8afc04b` marked parser/AST alignment and the call-target lesson complete. Analyzer callable-name diagnostics and interpreter dispatch remain assigned to their later milestones.

### Lessons

- [lesson] A parser method named for a precedence level does not necessarily return that node kind. Narrowing `call()` to `IdentifierExpr` caused a type error because the no-call path returns any primary expression; narrow only the actual `finishCall()` input and `CallExpr.callee` field.
- [technique] After `match(LEFT_PAREN)` succeeds, `previous()` is the attempted call's opening parenthesis. It supplies the exact diagnostic token while the current expression's discriminant proves whether the target is an identifier.
- [lesson] The common generic postfix grammar `primary ("(" arguments? ")")*` silently admits literals, grouped targets, and chained calls. Grammar and AST types must encode the language boundary, not merely rely on later semantic rejection.

## Semantic Function Calls and Arity

### Summary

Completed `docs/milestones/semantic-functions-calls-arity.md`. The analyzer now resolves identifier call targets as missing names, non-callable variables or built-in constants, user functions, or built-in functions. User-function calls must supply exactly the number of arguments declared by the function's parameters. Built-in signature and type validation remains assigned to the built-in call-error lesson.

### Analyzer and Data Model

- [decision] Scope declarations are a discriminated union. Variable entries retain a token; function entries retain a token and numeric arity.
- [decision] A function's arity is recorded from its parameter count when the function enters the global scope. Registration still happens before walking the body, so recursive calls resolve the function and its arity without hoisting later functions.
- [decision] Calling a variable or built-in constant reports `Cannot call '<name>' because it is not a function.` at the callee identifier. Missing callees continue to report `Cannot find name '<name>'.`
- [decision] User-function arity mismatches report `Function '<name>' expects <expected> arguments, but got <actual>.` at the callee identifier.
- [decision] Built-in arity checking is deferred to `docs/milestones/semantic-built-in-call-errors.md`; this milestone only distinguishes callable built-in functions from non-callable constants.
- [technique] `isBuiltInName()` uses `Object.hasOwn()` as a truthful type guard before indexing the exhaustive built-in registry with a token lexeme.

### Tests and Lessons

- Analyzer coverage now pins undefined calls, variables and built-in constants used as call targets, accepted built-in functions, accepted user-function arity, and both too-few and too-many user-function arguments.
- [lesson] `reservedNames` cannot answer whether an identifier is callable. It intentionally combines syntax keywords, built-in functions, and built-in constants; using it in `onCall()` initially rejected valid calls such as `print(1)`. Callability must come from scope declaration kind or built-in registry kind.
- [lesson] `Object.hasOwn(registry, name)` is a runtime check but does not narrow an arbitrary `string` to the registry's key union. A type-predicate helper communicates the checked fact to TypeScript without an unchecked cast.
- [lesson] Callee diagnostics and arity diagnostics do not stop traversal of argument expressions, allowing independent argument diagnostics to be collected.
